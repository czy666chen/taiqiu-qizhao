# 账号自定义牌库路线图

> 状态：规划中
>
> 适用版本：v6.x 之后
>
> 最后更新：2026-08-24

## 1. 目标

将官方自带牌库的产品入口收敛为“全量牌库”，同时允许已登录玩家：

1. 从全部官方卡牌中选择卡牌，创建自己的牌组；
2. 创建、编辑和删除账号下的自定义卡牌；
3. 在一个牌组中混用官方卡牌和自己的自定义卡牌；
4. 将牌组及自定义卡牌保存在对应账号中，并可跨设备使用；
5. 在普通对局、八球对局和实时房间中选择自己的牌组；
6. 保证已经开始或已经结束的对局不受后续牌组编辑影响。

## 2. 范围与非目标

### 本期范围

- 官方牌库选择界面只展示“全量牌库”；
- 私有自定义卡牌与私有自定义牌组；
- 账号级持久化、跨设备读取；
- 牌组显式保存和不可变版本快照；
- 开局时解析牌组并固化完整快照；
- 旧牌组、旧对局和本机存档的兼容迁移；
- D1 用量、配额和异常监控。

### 暂不包含

- 玩家之间公开分享或市场化发布牌组；
- 协同编辑同一个牌组；
- 自定义图片上传、图片审核和内容推荐；
- 复杂的牌组分支、版本比较与版本回滚界面；
- 管理员审核工作台。

`decks.visibility` 现有的 `shared` 值暂不开放产品入口，避免本期引入分享权限与内容治理问题。

## 3. 当前状态

- 官方牌库目前有 `complete`、`light`、`competitive`、`safe` 四种，卡牌定义保存在代码中；
- 当前共有 50 种官方卡牌、51 个牌实例；
- D1 已有 `decks`、`deck_versions`、`deck_cards` 表，并通过 `owner_user_id` 归属账号；
- 当前 `/api/decks` 只返回牌组元数据，单牌组接口也没有返回版本快照；
- 当前牌组写入主要用于旧本机数据迁移，尚未形成完整的日常创建、编辑、删除 API；
- 实时房间的 `deckId` 仍限定为官方牌组 ID，开局逻辑直接从代码中的官方牌库生成卡牌；
- 对局快照已经具备保存牌组信息的基础，但自定义卡牌仍需扩展类型和校验。

知识图谱显示该改动会影响约 25 个关联文件，关键入口包括 `DecksPage`、`SetupDialog`、`EightBallSetupDialog`、`createMatchCardState` 和实时房间牌组逻辑，整体按高风险跨模块变更处理。

## 4. 核心设计决策

### 4.1 官方卡牌不复制到每个账号

官方卡牌继续以代码中的稳定 `definitionId` 为唯一标识。D1 只保存玩家选择了哪些官方卡牌，不为每个账号复制标题和效果。

产品界面只展示“全量牌库”。为了兼容旧对局，旧的 `light`、`competitive`、`safe` 解析能力先保留为隐藏兼容层，不再允许新建对局选择。确认旧存档均可由自身快照恢复后，再单独评估删除兼容代码。

### 4.2 自定义卡牌独立保存

新增账号级 `custom_cards` 表。玩家创建的卡牌可以被多个自己的牌组引用，避免重复保存。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | UUID 主键 |
| `owner_user_id` | 所属账号，级联删除 |
| `title` | 卡牌标题 |
| `effect` | 卡牌效果 |
| `default_quantity` | 加入牌组时的默认数量 |
| `safety_level` | `low` / `medium` / `review` |
| `safety_note` | 可选安全提示 |
| `created_at` / `updated_at` | 时间戳 |
| `deleted_at` | 软删除时间 |

必须建立 `(owner_user_id, deleted_at, updated_at)` 索引。所有读取和修改同时校验 `id` 与 `owner_user_id`，禁止仅凭卡牌 UUID 授权。

### 4.3 当前牌组与历史版本分离

前端编辑过程保留在本机状态中，不在每次勾选时写 D1。玩家点击“保存”后：

1. 更新 `decks` 元数据；
2. 新增一个不可变的 `deck_versions` 快照；
3. 将 `decks.current_version` 指向新版本；
4. 使用 `operationId` 保证重试幂等。

第一期直接使用已有的 `deck_versions.snapshot_json` 保存完整版本，不同时写入 `deck_cards`，以减少 D1 行写入和实现复杂度。`deck_cards` 标记为保留表，后续只有在确实需要卡牌级查询、分享检索或统计时才启用。

建议快照格式：

```json
{
  "formatVersion": 1,
  "name": "周五朋友局",
  "cards": [
    {
      "source": "official",
      "definitionId": "card-001",
      "quantity": 1
    },
    {
      "source": "custom",
      "definitionId": "自定义卡牌 UUID",
      "quantity": 2,
      "snapshot": {
        "title": "再来一杆",
        "effect": "本回合未进球时可以再击打一杆。",
        "safetyLevel": "low"
      }
    }
  ]
}
```

自定义卡牌在保存牌组版本时复制必要展示字段到快照。以后即使原自定义卡牌被编辑或删除，旧牌组版本和历史对局仍能准确恢复。

### 4.4 开局固化完整快照

开局请求不直接信任客户端提交的卡牌标题和效果，只提交牌组引用：

```ts
type DeckRef =
  | { kind: "official"; id: "complete"; version: 1 }
  | { kind: "user"; deckId: string; versionNo: number };
```

Worker 校验牌组归属后，从 D1 读取指定版本，解析并校验完整卡牌列表，再把不可变的牌组快照交给本地对局状态或 Durable Object。房间运行期间不再读取可编辑的当前牌组。

## 5. 默认产品限制

以下限制用于控制滥用、响应大小和免费额度，可在上线数据稳定后调整：

| 项目 | 默认上限 |
| --- | ---: |
| 每个账号的有效牌组 | 20 个 |
| 每个账号的有效自定义卡牌 | 100 张 |
| 单个牌组的卡牌种类 | 100 种 |
| 单个牌组的卡牌实例总数 | 200 张 |
| 单种卡牌数量 | 10 张 |
| 牌组名称 | 1–40 字符 |
| 卡牌标题 | 1–40 字符 |
| 卡牌效果 | 1–500 字符 |
| 安全提示 | 0–300 字符 |
| 单次保存请求体 | 64 KB |

所有限制必须在服务端重复校验；前端限制只用于即时反馈。

## 6. API 路线

### 卡牌目录

- `GET /api/card-catalog`
  - 返回全量官方卡牌和当前账号未删除的自定义卡牌；
  - 响应包含官方目录版本，支持客户端缓存；
  - 未登录用户只获得官方卡牌。

### 自定义卡牌

- `GET /api/custom-cards`
- `POST /api/custom-cards`
- `PATCH /api/custom-cards/:id`
- `DELETE /api/custom-cards/:id`

写接口要求同源、已登录、字段白名单、长度校验和账号归属校验。删除采用软删除；已保存的牌组版本继续使用其中的卡牌快照。

### 自定义牌组

- `GET /api/decks`：返回当前账号牌组列表；
- `POST /api/decks`：创建牌组及第一个版本；
- `GET /api/decks/:id`：返回元数据和当前版本快照；
- `PUT /api/decks/:id`：显式保存新版本，携带 `expectedVersion` 与 `operationId`；
- `DELETE /api/decks/:id`：软删除牌组；
- `GET /api/decks/:id/versions`：后续需要版本历史界面时再开放。

版本冲突返回 `409`，并返回服务端当前版本号。首期不自动合并两个设备同时编辑的内容。

## 7. 分阶段实施

### 阶段 0：基线与契约

预计：0.5–1 个工程日。

- [ ] 固定官方卡牌 ID，补充重复 ID 和数量校验测试；
- [ ] 定义 `DeckRef`、牌组快照和自定义卡牌类型；
- [ ] 确认默认配额与字段长度；
- [ ] 记录当前 D1 数据库大小、每日读写行数和现有错误率；
- [ ] 为新快照增加 `formatVersion`，确定旧数据解析策略。

退出条件：类型契约、配额、兼容策略和监控基线均已明确。

### 阶段 1：数据库与后端 CRUD

预计：1.5–2 个工程日。

- [ ] 新增 `custom_cards` 迁移和 Drizzle schema；
- [ ] 实现卡牌目录与自定义卡牌 CRUD；
- [ ] 补齐牌组创建、读取、保存新版本和删除 API；
- [ ] 牌组保存使用 D1 batch，保证牌组与版本指针同时成功或失败；
- [ ] 增加 `operationId` 幂等回执和 `expectedVersion` 冲突控制；
- [ ] 导出账号数据时包含自定义卡牌、牌组版本和必要快照；
- [ ] 删除账号时确认新表通过外键级联清理。

退出条件：两个账号之间无法读取或修改对方资源；重复请求不会产生重复版本。

### 阶段 2：牌库与编辑器界面

预计：1.5–2 个工程日。

- [ ] 官方牌库入口只展示“全量牌库”；
- [ ] 牌组页面展示“官方卡牌”和“我的卡牌”两个来源；
- [ ] 支持搜索、勾选、数量调整和牌组计数；
- [ ] 支持新建、编辑、复制和软删除自定义牌组；
- [ ] 支持新建、编辑和删除自定义卡牌；
- [ ] 编辑过程本地保存草稿，仅在明确点击“保存”时写云端；
- [ ] 对未保存、版本冲突、超出配额和网络失败提供明确反馈；
- [ ] 保证键盘操作、焦点状态和移动端可用性。

退出条件：登录玩家可以跨设备看到相同的自定义卡牌和牌组。

### 阶段 3：接入普通对局、八球与实时房间

预计：1–1.5 个工程日。

- [ ] 普通对局设置改用 `DeckRef`；
- [ ] 八球对局设置改用 `DeckRef`；
- [ ] 实时房间创建接口校验用户牌组归属和版本；
- [ ] `createMatchCardState` 支持解析后的通用牌组快照；
- [ ] `room-cards` 不再依赖 `OfficialDeckId` 才能运行；
- [ ] 开局后仅使用固化快照，删除或编辑原牌组不影响当前房间；
- [ ] 房间投影继续隐藏未抽到的卡牌内容，避免信息泄露。

退出条件：三种对局入口均能使用混合牌组，且进行中的对局不受牌组后续修改影响。

### 阶段 4：兼容迁移与清理官方入口

预计：0.5–1 个工程日。

- [ ] 新建对局的官方牌组选择只允许 `complete`；
- [ ] 本机尚未开始的旧草稿若选择其他官方牌组，迁移为 `complete` 并提示一次；
- [ ] 已开始和历史对局保留自身牌组快照，不改写结果；
- [ ] 旧实时房间恢复路径继续识别旧官方 ID；
- [ ] 确认旧存档恢复覆盖后，将其他官方牌组移入隐藏兼容模块；
- [ ] 不在本阶段物理删除 `deck_cards`，避免不必要的破坏性迁移。

退出条件：新入口只有全量牌库，旧对局仍可查看、恢复和继续。

### 阶段 5：测试、灰度与发布

预计：1–1.5 个工程日。

- [ ] 单元测试：快照解析、数量限制、官方 ID、删除后的快照稳定性；
- [ ] Worker 集成测试：账号隔离、CRUD、幂等、版本冲突、配额、导出与删号；
- [ ] 实时测试：自定义牌组开房、抽牌、出牌、跳过和重新发牌；
- [ ] E2E：创建自定义卡牌 → 创建牌组 → 开局 → 修改原牌组 → 当前局保持不变；
- [ ] E2E：另一账号无法访问牌组；
- [ ] E2E：旧本机牌组和历史对局兼容；
- [ ] 先发布 preview，观察至少一个完整测试周期；
- [ ] 生产发布后监控 D1 用量、API 4xx/5xx、版本冲突率和房间恢复错误。

退出条件：全部自动化测试通过，preview 无阻断问题，生产回滚路径可用。

## 8. D1 免费额度预算

截至 2026-08-24，Workers Free 下的 D1 关键额度为：每天 500 万行读取、每天 10 万行写入、单数据库 500 MB、账号总存储 5 GB。免费额度在每日 00:00 UTC 重置。

本项目的生产环境使用单个 D1 数据库，因此首先受单库 500 MB 限制，而不是账号总计 5 GB 限制。

### 牌库数据估算

- 全部 50 个官方卡牌 ID 的紧凑 JSON 快照约 618 字节；
- 按每账号 5 个牌组、20 张自定义卡牌估算，牌库数据通常约 20–50 KB/账号；
- 忽略对局历史等其他数据时，500 MB 大约可容纳 1 万–2.5 万个此类账号；
- 实际容量应给对局、事件、索引、审计和同步回执预留至少 40%。

### 写入策略

- 禁止每次勾选卡牌都创建 `deck_versions`；
- 使用本地草稿和显式保存；
- 每次保存只新增一个版本，并更新一个牌组指针；
- 对相同 `operationId` 返回已有结果；
- 不在第一期同时维护 `snapshot_json` 和逐卡 `deck_cards` 双写。

### 预警阈值

| 指标 | 黄色预警 | 红色预警 |
| --- | ---: | ---: |
| 单库大小 | 300 MB | 400 MB |
| 每日读取行数 | 300 万 | 400 万 |
| 每日写入行数 | 6 万 | 8 万 |
| 牌组保存失败率 | 1% | 3% |
| 版本冲突率 | 3% | 8% |

达到黄色预警时优先检查未命中索引的查询、过密自动保存、无限增长的版本和同步回执；达到红色预警时暂停高频非必要写入，并评估数据保留策略或 Workers Paid。

官方额度来源：

- [Cloudflare D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/)
- [Cloudflare D1 Limits](https://developers.cloudflare.com/d1/platform/limits/)
- [Cloudflare D1 Metrics and analytics](https://developers.cloudflare.com/d1/observability/metrics-analytics/)

## 9. 数据保留与维护

- 当前牌组版本永久保留；
- 历史版本首期全部保留，数据稳定后再决定是否只保留最近 20 个非对局引用版本；
- 已被历史对局引用的版本不得清除；
- 自定义卡牌和牌组使用软删除，账号删除时物理级联清理；
- 同步回执和审计日志沿用项目已有的保留任务；
- 定期执行外键检查和数据库快速检查；
- 任何清理任务先提供 dry-run 数量和预计释放空间。

## 10. 安全与内容边界

- 所有自定义内容按不可信输入处理，React 页面只以文本渲染，不解释 HTML；
- 自定义卡牌创建、编辑、牌组保存均需要有效会话和同源校验；
- 牌组引用的每张自定义卡牌必须属于当前账号；
- 开房时由服务端重新解析牌组，不能使用客户端伪造的卡牌效果；
- 日志不记录完整自定义卡牌正文，只记录资源 ID、操作结果和错误类型；
- 自定义卡牌默认私有；未来开放分享前必须补充举报、审核和下架机制；
- 对身体动作类卡牌保留安全等级和安全提示字段。

## 11. 验收标准

以下条件全部满足才视为完成：

1. 新用户只能看到一个官方“全量牌库”；
2. 登录玩家能创建自定义卡牌，并在多个自己的牌组中复用；
3. 玩家能从官方卡牌和自定义卡牌中自由组合并保存牌组；
4. 退出登录并在另一设备登录后，牌组内容一致；
5. 玩家不能通过修改 URL、UUID 或请求体访问其他账号资源；
6. 同一个保存请求重试不会创建重复版本；
7. 两台设备并发保存时不会静默覆盖，旧版本请求收到 `409`；
8. 已开始的对局不受原牌组或自定义卡牌后续编辑、删除影响；
9. 普通对局、八球和实时房间均可使用自定义牌组；
10. 旧对局和旧本机存档可以恢复，且不改变历史卡牌内容；
11. 自动化测试、数据库检查、preview 验证和生产监控均通过；
12. 生产环境 D1 用量未超过本路线图的黄色预警阈值。

## 12. 推荐提交拆分

为降低回滚和审查风险，建议至少拆成以下提交或 PR：

1. `feat(db): add account-owned custom cards`；
2. `feat(api): add custom card and deck version CRUD`；
3. `feat(ui): add account deck editor`；
4. `feat(cards): resolve user deck snapshots for matches`；
5. `feat(realtime): support user decks in rooms`；
6. `refactor(cards): expose only the complete official deck`；
7. `test(cards): cover ownership versioning and legacy recovery`；
8. `docs(cards): document quotas monitoring and operations`。

每个提交都应同时包含相应测试；数据库迁移与依赖它的 Worker 代码应在同一可部署单元中发布。
